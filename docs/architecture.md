# 実装構成

本書をアプリケーションの構成と責務の設計とする。
ここに示すモジュールは論理境界である。

## 技術スタック

| 技術 | 責務 |
| --- | --- |
| Python | サーバーと解析処理、型付きの内部モデル |
| FastAPI | HTTP受付、入力検証、解析サービス呼出し |
| Jinja2 | サーバーレンダリング |
| HTML/CSS | 入力フォーム、結果、レスポンシブ表示 |
| 必要最小限のJavaScript | アップロード補助、結果表示の補助 |
| MediaPipe Face Landmarker | 顔検出、ランドマーク、変換行列 |
| NumPy | ベクトルと行列の演算 |
| SciPy | 統計分布、距離計算の数値処理 |
| Pillow / NumPy | 安全な画像デコード、EXIF Orientation適用、RGB画素と寸法 |
| OpenCV | 画質評価など、後続の画像処理 |
| Docker | Pythonと依存ライブラリを含む再現可能な実行環境 |
| docker compose | MVPのローカル起動と環境構成 |

React等のSPAはMVPでは採用しない。
ホストへのPythonやMediaPipeの直接インストールを前提とせず、コンテナ内で管理する。
Dockerfileとcomposeによる環境を用意し、Face Landmarkerモデルはbuild時に取得して固定チェックサムを検証する。
本番インフラ、公開URL、ワーカー数はTODOとする。

## 責務と依存方向

| 境界 | 内部責務 | 受け渡すもの |
| --- | --- | --- |
| `web` | HTTP、フォーム、Jinja2、`result_view` | 入力画像と参照群、表示用結果 |
| 解析サービス | 各工程の順序、失敗処理、画像寿命の管理 | 解析要求と型付き結果 |
| `image_processing` | 安全なデコード、EXIF除去、色変換、縮小 | 画像配列と実寸法 |
| `landmarks` | MediaPipe Face Landmarkerの生成・実行、SDK型の変換 | 内部型の顔別ランドマークと変換行列 |
| `feature_extraction` | `measurements` の距離計算、`features` の比率生成 | 固定順の3次元特徴ベクトル |
| `validation` | `image_validation`、`pose_validation`、顔数、品質 | 判定コードと理由、品質結果 |
| `reference_data` | 公開統計量の読込み、出典と版の管理 | 群別の参照値、参照モデル |
| `statistics` | デルタ法、共分散、z、距離、スコア | 特徴ベクトルから統計結果 |
| `result_view` | 統計結果の表示名、方向説明、計測線の表示情報 | HTML用のデータ |

上表はアプリケーションの処理を責務別に分けたものである。
解析サービスから各責務を呼び、統計処理をWebテンプレートや画像処理に埋め込まない。
`statistics` は画像、MediaPipe型、HTTP、Jinja2を受け取らず、数値と参照モデルだけで動くようにする。
距離計算、比率、統計式、閾値判定は副作用のない関数としてテスト可能にする。

モデルのロードと再利用、同時実行時のMediaPipeインスタンス管理は要検証である。現段階では解析ごとにインスタンスを生成して閉じる。
スレッド安全性を仮定せず、[資源制限](non-functional-requirements.md)と合わせて実装方式を決める。

## 統計モデルの交換境界

統計サービスの入力は、固定順の特徴ベクトル、参照群ID、モデルモード、版と設定情報とする。
出力は、項目別zスコア、総合距離、スコア、その解釈と近似注記を持つ共通の結果型とする。
公開統計量の読込みとモデル構築は参照データ側と統計側の協調で行い、画像ごとに外部サイトを取得しない。
転記済みCSVから生成した `reference_data.json` を参照データ側で読み込み、統計モデル層が比率の統計量とスコアを計算する。
生成経路とJSONの形式は[参照データ](dataset.md)に定義する。

`summary_delta` と `empirical` は同じインターフェースを満たす。
MVPでは前者だけを実装し、後者の未取得データを仮の個票で補わない。
将来切り替えるときもフィールドの意味と型を保ち、`model_mode` と注記で理論近似と経験分布の違いを伝える。
スコア分布の変更が画面や画像計測の変更を要求しない構成とする。

## HTTPと内部結果

| HTTP | 責務 |
| --- | --- |
| `GET /` | 写真条件、参照群選択、アップロードフォームを返す |
| `POST /analyze` | 画像と参照群を受け取り、解析して結果画面を返す |

MVPはサーバーレンダリングを基本とし、独立したJSON公開APIを必須としない。
解析関数／サービス層はHTTPから独立させ、将来API化できる内部結果モデルを持つ。

| フィールド | 意味 |
| --- | --- |
| `reference_group` | ユーザーが選んだ比較群 |
| `model_mode` | `summary_delta` または将来の `empirical` |
| `score` | 平均顔近似スコア |
| `distance` | 平均顔からの距離 |
| `features` | 名前と順序を固定した3比率 |
| `z_scores` | 項目別の標準化値 |
| `quality_checks` | 品質の判定結果 |
| `approximation_notice` | モデルの制約を説明する注記 |
| `algorithm_version` | 画像計測と計算処理の版 |
| `reference_model_version` | 参照値、モデル方式と構築設定を追跡する版 |

最後の2項目は今回の再現性要件として追加する。
型、詳細スキーマ、validation失敗時のHTTPステータスは実装開始時のTODOである。
顔画像や生ランドマーク全量を通常の統計結果へ混ぜない。
計測線の重畳に必要な画像情報はリクエスト内の表示処理だけに渡し、再取得用の永続URLを発行しない。

## 設定の管理

モデルパス、モデル版、採用点、validation閾値、正則化、画像受理上限を設定としてまとめる。
設定変更時には版または設定識別子で追跡する。
秘密情報は設定ファイルと分離し、Gitへ置かない。
設定形式、環境変数名、health／readinessのパスはTODOである。
