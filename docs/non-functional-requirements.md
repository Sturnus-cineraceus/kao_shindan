# MVPの非機能要件

本書は画像破棄とログ制限を含むMVPの運用要件を定める。
SLAや性能保証値は未決定である。
未計測の値は初期目標、要計測、要負荷試験として扱う。

## 性能と資源制限

MVPは大量アクセスを前提とせず、1リクエストの処理が暴走しないことを要求する。
アップロード、デコード、推論、計算の各段階で資源使用を制限し、異常画像で無制限にCPUやメモリを消費しないようにする。

| 項目 | 要件と確認方法 | 状態 |
| --- | --- | --- |
| 単一画像解析時間 | 受付から応答までと工程別時間を測る | 初期目標の数値はTODO、要計測 |
| 同時アクセス | 単一リクエストで確認後、並列数ごとに遅延とメモリを測る | 同時利用者数はTODO、要負荷試験 |
| CPU使用量 | 推論中のピーク、継続時間、並列実行時の飽和を確認する | 要計測 |
| メモリ使用量 | モデル常駐量、デコード時ピーク、反復後の増加を確認する | 上限はTODO、要計測 |
| モデルロード | 初期化時間と失敗時の挙動を測る | 要計測 |
| 初回とウォーム状態 | 起動後初回とモデルロード済みの処理を分けて報告する | 要計測 |
| ファイルサイズ上限 | アップロード中にバイト上限を適用する | 値はTODO、実装時に必須 |
| 解像度上限 | 幅、高さ、総ピクセル数を制限する | 値はTODO、実装時に必須 |
| 解析前リサイズ | 必要なら縦横比を維持して縮小する | 長辺上限、補間は要検証 |
| 実行上限 | 実行時間、同時実行数、待ち行列を有界にする | 値と方式はTODO、要負荷試験 |

HTTPタイムアウトだけで推論処理が停止したとは扱わない。
必要なら解析の実行単位を分離して回収できる方式を検討する。
解析前リサイズは、デコード前の総ピクセル数制限の代替にはならない。
画質評価用の縮小サイズは[validation.md](validation.md)を正本とする。

## 可用性と復旧

MVPでは高可用クラスタと厳密な稼働率SLAを必須にしない。
プロセス異常時の再起動とDocker再起動で復旧できる構成を要求する。
1件の異常画像がWebプロセス全体を落とさないよう、例外処理と資源上限を設ける。

一時ファイルが残って復旧不能にならないようにする。
通常終了と例外ではリクエスト単位で確実に削除し、強制終了に備えて専用一時領域の容量管理と残存ファイル回収を設計する。
回収方式と実行時期はTODOとし、任意ディレクトリを削除する構成を避ける。
推論が異常終了した場合の影響範囲と再起動方法は実装時に検証する。

## 入力とWebのセキュリティ

- MIME typeと拡張子だけを信用せず、実画像としてdecode可能か確認する。
- 許可形式を限定する（暫定案はJPEG／PNG、最終リストはデコーダ検証後に決定）。
- 受信バイト数、幅、高さ、総ピクセル数に上限を設ける。
- 展開前の寸法検査、デコーダの制限、資源制限によりdecompression bombへ対処する。
- 破損画像、想定外の複数フレーム、未対応形式の扱いを明示し、安全に拒否する。
- 任意ファイルパスを入力として受け取らず、アップロードファイル名を保存パスに使わない。
- 一時保存が必要ならサーバーが生成した識別子と専用領域を使用する。
- EXIFを解析用画像と重畳画像へ引き継がない。
- Jinja2のエスケープを維持し、ファイル名やユーザー入力をHTMLへ無加工で埋め込まない。
- `POST /analyze` にCSRF対策を設ける。
- セキュリティヘッダを設定し、画面に必要な機能と整合するCSP等を検討する。
- 顔画像を含む応答を共有キャッシュへ残さない方針とし、レスポンスのキャッシュ制御を設計する。
- 依存ライブラリの版を固定し、脆弱性と更新を定期的に確認する。
- トークン、鍵、接続情報などの秘密情報をGitへ置かない。

CSRFの具体方式、CSP等の値、公開時のHTTPS終端、リクエスト制限の配備先はTODOである。
方式の未決定を理由に対策自体を省略しない。

## プライバシーと画像寿命

アップロード顔画像を永続保存しない。
MVPの解析はローカルサーバー内で完結し、顔画像を第三者サービスへ送信しない。
モデルや参照データはサーバー内で利用できる状態にし、リクエストごとに画像を外部APIへ渡さない。

EXIFは解析前に除去する。
元画像、中間画像、一時ファイルは処理完了後またはリクエスト終了時に破棄し、失敗時も同じ扱いとする。
結果URLから元画像を再取得できる構造を作らない。
結果画面の重畳画像はその応答のために生成し、サーバーに永続化しない。
メモリ上の参照解放を行うが、物理メモリの完全消去を保証したとは説明しない。

通常ログにも障害ログにも、画像、Base64、EXIF位置情報、生ランドマーク全量を残さない。
フォーム全体や内部画像配列を例外メッセージへ展開しない。
将来の画像保存には明示的同意、目的、期間、アクセス権、削除方法の別途設計を要する。
保存機能の採用はTODOであり、同意のない統計改善目的の保存をしない。

## ログに残す情報

| 残してよい情報 | 残さない情報 |
| --- | --- |
| request id | 顔画像と中間画像 |
| HTTP status | Base64画像 |
| 処理時間と工程別時間 | EXIFと位置情報 |
| validation結果コード | 生ランドマーク全量 |
| 使用モデルのバージョン | 不要な個人特定情報 |
| エラー種別 | アップロード本文や画像を含む例外ダンプ |

個別の特徴ベクトルや選択集団も通常ログの必須項目にせず、調査に不要なら記録しない。
逆プロキシ、APM、コンテナのログ設定も同じ方針を適用する。
ログ保持期間、閲覧権限、集計方式はTODOとする。

## 監視と運用

| 監視候補 | 目的 |
| --- | --- |
| health endpoint | Webプロセスが応答するか |
| readiness | モデルと参照データがロードされ解析を受け付けられるか |
| エラー率 | 内部障害と想定された品質拒否を分けて把握する |
| 処理時間 | 初回、ウォーム状態、工程別の悪化を把握する |
| メモリ使用量 | ピークと反復による増加を確認する |
| コンテナ再起動 | 異常終了と復旧を確認する |
| ディスク使用量 | 一時領域とログによる逼迫を検知する |

health／readinessのパス、通知閾値、監視間隔はTODOとする。
監視のために顔画像を保存せず、外部監視製品は固定しない。

## 再現性と保守性

同じ画像、MediaPipeモデル、reference data、algorithm version、configurationなら同じ結果になることを基本要件とする。
浮動小数点やプラットフォーム差の許容誤差は要検証であり、ビット単位の一致を未検証で保証しない。
画像処理の順序、モデル実体、参照値、設定、依存ライブラリの版を固定して記録可能にする。
結果JSON等の内部結果には `algorithm_version` と `reference_model_version` を持たせる。
設定識別子の持たせ方はTODOとする。

型ヒント、モジュール責務分離、テスト可能な純粋関数を用いる。
計算式をUIコードに書かず、閾値は設定で管理する。
統計モデルを画像処理から切り離し、公開統計量モデルから個票モデルへ交換可能にする。
外部依存は版を固定し、更新時は回帰テストで影響を確認する。

## アクセシビリティと端末

MVPはレスポンシブWeb画面とし、スマートフォンとデスクトップで入力と結果を確認できるようにする。
対応対象は現行主要ブラウザとし、正式なサポート範囲は検証後に決定する。

色だけで結果を表さず、グラフへ数値と説明文を併記する。
フォームにラベルを付け、エラー理由を文章で表示し、キーボードで選択と送信を行えるようにする。
計測線の画像だけに情報を閉じ込めず、項目名と方向も文章で確認できるようにする。
正式な適合基準や検証端末一覧はTODOとする。

## ログ出力

アプリは標準出力／標準エラーとUTF-8の `/app/logs/app.log` に同時出力する。ホスト側はCompose bind mountの `./logs/app.log`。設定値と機密情報を残さない要件は上記の通りとする。

## ログ

共通logging設定でconsoleとUTF-8ファイルへ同時出力する。既定は `/app/logs/app.log`（ホスト側 `./logs/app.log`）、10MBでサイズローテーション、5世代保持。`LOG_LEVEL`、`LOG_FILE`、`LOG_MAX_BYTES`、`LOG_BACKUP_COUNT`で変更する。アプリ単体の既定レベルはINFO、Compose開発環境はDEBUG。初期化を繰り返してもhandlerを重複させない。ログに画像や全ランドマーク座標を記録しない。
